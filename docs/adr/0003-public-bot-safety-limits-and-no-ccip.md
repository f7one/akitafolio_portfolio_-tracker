# ADR-0003: Лимиты публичного бота и отключение CCIP Read

- **Статус:** accepted
- **Дата:** 2026-08-24
- **Владелец решения:** project owner

## Контекст

Публичные Telegram-команды могут развернуть fan-out RPC-вызовов по сетям,
адресам, токенам и DeFi. Синхронный Web3 внутри async handler блокировал event
loop. Кроме того, пользовательский ERC20 contract мог инициировать EIP-3668
CCIP Read — внеплановый off-chain HTTP request.

## Решение

1. Отключить `global_ccip_read_enabled` для каждого Web3 HTTP provider: продукт
   не использует CCIP Read.
2. Применить process-local limiter для дорогих команд: 6 запросов/минуту на
   пользователя, burst 2, один запрос пользователя одновременно.
3. Ограничить данные пользователя: 5 ETH-адресов, 10 BTC-адресов, 2 xpub,
   10 custom ERC20; общий предел блокирующих RPC-вызовов — 8.
4. Выполнять синхронные Web3 calls через `asyncio.to_thread` внутри общего
   semaphore. Значения задаются `AKITAFOLIO_*` settings.

## Последствия

- Нагрузка на один процесс и Infura предсказуема; один пользователь не может
  занять все worker slots.
- CCIP-enabled contracts не поддерживаются. Если это станет продуктовой
  необходимостью, потребуется allowlist/isolated transport и новый ADR.
- Limiter неперсистентный и рассчитан на один systemd process. При горизонтальном
  масштабировании его нужно заменить shared store, например Redis.

## Рассмотренные альтернативы

### Без лимитов

Отклонено: позволяет дешёвый abuse и блокирование event loop.

### Redis и distributed rate limiting сейчас

Отклонено: на одном VPS это добавляет инфраструктуру без оправданной пользы.

### Разрешить CCIP Read с фильтрацией URL

Отклонено: feature не нужен боту, а allowlist требует отдельной модели доверия.
